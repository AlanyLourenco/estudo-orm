O descompasso de impedância

DiferençaNo mundo dos objetosNo banco relacional
GranularidadeMuitas classes pequenas: Cliente tem um EnderecoPoucas tabelas largas: endereço vira colunas de cliente
HerançaAluno e Professor herdam de PessoaNão existe herança entre tabelas

Por que o nome “impedância”?

Vem da engenharia elétrica: com impedâncias diferentes, a energia não passa bem de um circuito para o outro. É como levar um carregador de pinos redondos para um país de pinos chatos: o encaixe não acontece.

O adaptador resolve o encaixe, mas não muda a voltagem: o ORM esconde as diferenças, não as elimina.

Parte 02O que é ORM

ORM: a ponte objeto-relacional

ORM é a técnica que mapeia classes para tabelas e converte sozinha objetos em linhas (ao salvar) e linhas em objetos (ao ler)

Um objeto vira uma linha

1 · Você escreve Java 
Aluno ana = new Aluno();
ana.setNome("Ana Souza");
ana.setEmail("ana@uni.br");
ana.setCurso("SI");
em.persist(ana);
→
2 · O ORM gera o SQL 
INSERT INTO aluno
  (nome, email, curso)
VALUES
  ('Ana Souza',
   'ana@uni.br', 'SI');
→
3 · A tabela ganha uma linha
idnomecurso
1Bruno LimaADS
2Carla DiasSI
3Ana SouzaSI

O id 3 foi gerado pelo banco e copiado para o objeto: depois do persist, ana.getId() devolve 3.

Volta em.find(Aluno.class, 3L) → SELECT … WHERE id = 3 → objeto Aluno preenchido

Onde o ORM mora no sistema

O que o ORM faz por você

  1. Lê o mapeamento (anotações ou XML)
  2. Gera INSERT, SELECT, UPDATE, DELETE
  3. Converte tipos: LocalDate ↔ DATE
  4. Guarda objetos já lidos (cache)
  5. Percebe mudanças (dirty checking)
  6. Adapta o SQL a cada banco
  7. Controla transações: tudo ou nada

Parte 03Entidades

O que é uma entidade?

Uma classe cujos objetos precisam ser guardados e têm identidade própria: cada um é único e pode ser encontrado de novo.

Alegoria · A secretaria

Regras de uma entidade JPA

  • Anotada com @Entity
  • Tem um identificador com @Id
  • Tem construtor sem argumentos
  • Não é final (o ORM cria proxies)

É entidade?

Sim: Aluno, Turma, Pedido, Produto

Não: Endereço (só um valor), um total calculado

A entidade no código e a tabela gerada

Aluno.javaJPA
@Entity
@Table(name = "aluno")
public class Aluno {
    @Id
    @GeneratedValue(strategy =
        GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false,
            length = 100)
    private String nome;
    @Column(unique = true)
    private String email;
    protected Aluno() { }
}

Aluno.java · Carteirinha.javaJPA
@Entity
public class Aluno {
    @Id @GeneratedValue
    private Long id;
    private String nome;
    @OneToOne
    @JoinColumn(name = "carteirinha_id",
                unique = true)
    private Carteirinha carteirinha;
}
@Entity
public class Carteirinha {
    @Id @GeneratedValue
    private Long id;
    private String codigo;
}
  • @JoinColumn: qual coluna guarda a FK
  • unique = true: duas pessoas nunca dividem a mesma carteirinha
  • Bom para dados opcionais ou pesados (foto, prontuário)

Direção e dono do relacionamento

Uni: só um lado conhece o outro.
Bi: os dois se conhecem.

Cuidado

No bidirecional, atualize os dois lados em Java.

O dono é o lado com a FK na tabela. O outro lado usa mappedBy para não criar coluna repetida.

Alegoria

Carregar agora ou só quando precisar?

LAZY: o episódio só carrega quando você dá play

+ economiza consultas e memória
− erro se a sessão já fechou

EAGER: baixa a temporada inteira antes da viagem

+ dados sempre à mão
− traz o que talvez nunca seja usado

Padrão JPA …ToOne → EAGER…ToMany → LAZY Boa prática: tudo LAZY + JOIN FETCH

A ilusão da abstração: o problema N+1

A causa

Um laço dispara, sem ninguém ver, uma consulta por item, em vez de uma única consulta com JOIN.

O efeito

Cada ida ao banco soma tempo de rede: com muitos itens, a tela fica lenta. É o gargalo mais comum de um ORM mal configurado.

O que acontece numa transação

Matricular.javatransação
  em.getTransaction().begin();
1 Turma t =
    em.find(Turma.class, 7L);
2 Aluno a = new Aluno("Ana");
  a.setTurma(t);
3 em.persist(a);
4 t.setNome("Turma B");
5 em.getTransaction().commit();

Atenção: vale para chaves por SEQUENCE. Com IDENTITY, o banco precisa gerar o id, então o INSERT sai já no persist().

Unit of Work

Um carrinho de compras: o ORM anota tudo e só passa no caixa no commit.

Parte 06Além do básico

O desafio da herança no banco relacional

A abstração (POO)

Herança é nativa: Aluno e Professor reaproveitam tudo de Pessoa, de forma elegante.

A limitação (banco)

O modelo relacional não tem herança: só tabelas, colunas e chaves.

A missão do ORM

Achatar a árvore de herança em tabelas sem perder integridade, sem redundância exagerada e sem destruir o desempenho de leitura.

Três estratégias para mapear a herança

Tabela única

SINGLE_TABLE

Uma tabela para a família toda.

+ leitura rápida, zero JOIN
− colunas NULL para quem não usa

Por subclasse

JOINED

Tabelas normalizadas ligadas por FK.

+ sem NULL, boa integridade
− JOIN em toda consulta

Por classe

TABLE_PER_CLASS

Uma tabela por classe concreta.

+ tabelas independentes
− colunas repetidas; “todas as pessoas” pede UNION

Active Record vs Data Mapper

O objeto se salva

Rails · Django
aluno = Aluno.new(nome: "Ana")
aluno.save   # ele mesmo grava

O aluno leva a própria ficha à secretaria e a arquiva.

Alguém salva por ele

JPA · EF Core
Aluno aluno = new Aluno("Ana");
em.persist(aluno); // outro grava

O aluno só preenche; a secretaria arquiva.

Parte 08Balanço

O que o ORM traz de bom

Produtividade

Nada de copiar coluna por coluna.

Pensar em objetos

Aluno e Turma, não linhas e colunas.

Portabilidade

Trocar de banco muda o dialeto, não o código.

Segurança

Parâmetros vinculados contra SQL injection.

Cache e transações

Não relê o que já tem; agrupa gravações.

Um só lugar

O mapeamento fica junto da classe.

Onde o ORM pode atrapalhar

01

Abstração que vaza

Sem ler o SQL gerado, não dá para saber por que ficou lento.

02

Consultas N+1

Laços que disparam uma consulta por item.

03

Curva de aprendizado

Sessão, ciclo de vida, cascata, carregamento.

04

Relatórios pesados

Milhões de linhas: SQL direto é melhor.

05

Memória e CPU

Transformar cada linha em objeto custa.

06

“Mágica” demais

Cascata e dirty checking geram SQL escondido.

Dica Ligue o log de SQL (spring.jpa.show-sql=true) e leia o que o ORM envia.

A escolha da ferramenta: ORM vs SQL nativo

SQL nativo

Vantagens

Controle total das consultas; máximo desempenho em operações pesadas.

Cenários ideais

Relatórios e cargas em massa; consultas legadas complexas.

O preço

Código repetitivo e refatoração frágil.

ORM

Vantagens

Muito mais produtividade; integra naturalmente com orientação a objetos.

Cenários ideais

CRUD e cadastros; domínios com muitas regras e classes.

O preço

Risco de N+1 e SQL ineficiente se mal configurado.

Síntese: a matriz de decisão

O ORM é indispensável, mas nunca substitui conhecer bem o banco relacional e otimizar consultas.
